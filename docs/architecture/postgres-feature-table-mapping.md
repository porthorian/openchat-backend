# Postgres Feature-to-Table Mapping Matrix (v1)

Last updated: 2026-03-03
Status: Draft mapping based on currently implemented backend code paths.

## Legend
- Confidence: `High` means code-backed and clear mapping; `Medium` means likely but needs refactor details; `Low` means significant design uncertainty remains.
- `TBD` explicitly marks unresolved design areas.

| Feature Surface | Endpoint(s) | Current code path | Write tables (v1) | Read tables (v1) | Key constraints/indexes | Retention posture | Confidence | Notes / TBD |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Server directory | `GET /v1/servers` | `chat.Service.ListServersForUser` | `servers`, `server_memberships`, `users` | `servers` + `server_memberships` join | PK `servers.server_id`; PK `(server_id,user_uid)`; index on `(user_uid,membership_state)` | Durable | High | Filters by requester membership state instead of in-memory leave map |
| Leave server membership | `DELETE /v1/servers/{serverID}/membership` | `chat.Service.LeaveServer` | `server_memberships` (state + left_at) | `server_memberships` | PK `(server_id,user_uid)`; state check | Durable | High | Preserve per-user scoped leave behavior currently asserted in tests |
| Channel groups list | `GET /v1/servers/{serverID}/channels` | `chat.Service.ListChannelGroups` | `channel_groups`, `channels` | `channel_groups`, `channels` | FK to `servers`; index `(server_id, kind, position)` and `(server_id, channel_type, position)` | Durable | High | Reconstruct response shape with groups + nested channels |
| Member list | `GET /v1/servers/{serverID}/members` | `chat.Service.ListMembers` | `server_memberships`, `profiles`, `users` | `server_memberships` + `profiles` | FK chain + active membership filter | Durable | Medium | `status` is currently seeded string; source of truth for status is TBD |
| Message list | `GET /v1/channels/{channelID}/messages` | `chat.Service.ListMessages` | `messages`, `message_mentions`, `message_attachments` | same | index `(channel_id, created_at DESC, message_id DESC)` | Durable | High | Use keyset pagination upgrade later; limit behavior preserved |
| Message create | `POST /v1/channels/{channelID}/messages` | `chat.Service.CreateMessage` | `messages`, `message_mentions`, `message_attachments`, `message_attachment_blobs`, optional `users` upsert | `messages` for reply target validation | FK `(server_id,channel_id)`; unique `(channel_id,idempotency_key)` partial index | Durable | High | Preserve reply-to + mention extraction semantics |
| Message attachments fetch | `GET /v1/channels/{channelID}/attachments/{attachmentID}` | `chat.Service.AttachmentContent` | `message_attachments`, `message_attachment_blobs` (default) or object-storage pointer metadata | same | PK `attachment_id`; FK to message/channel | Durable | High | Default storage is Postgres blobs; object storage backend is optional via configuration |
| Mention resolve | `GET /v1/channels/{channelID}/mentions:resolve` | `chat.ResolveMentionCandidates` | none (read path) | `messages`, `server_memberships`, `users` (and optionally `profiles`) | mention indexes by target/token | Durable metadata | Medium | Current resolver infers known UIDs from message history; policy-gated resolver TBD |
| Read ack get/put | `GET/PUT /v1/channels/{channelID}/read-ack` | `chat.GetReadAck`, `chat.UpdateReadAck` | `channel_read_acks` | `channel_read_acks`, `messages` | PK `(channel_id,user_uid)`; cursor index check | Durable | High | Monotonic semantics enforced in service logic; DB row used for persistence |
| Profile get/update | `GET/PUT /v1/profile/me` | `profile.Service.GetOrCreate/Update` | `profiles`, optional `profile_avatar_assets` | `profiles` | PK `profiles.user_uid`; profile_version check in app | Durable | High | Optimistic conflict behavior (`If-Match`) maintained |
| Profile avatar upload/get | `POST /v1/profile/avatar`, `GET /v1/profile/avatar/{assetID}` | `profile.Service.UploadAvatar/AvatarContent` | `profile_avatar_assets`, `profile_avatar_blobs` (default) or object-storage pointer metadata | same | PK `avatar_asset_id` | Durable | High | Default storage is Postgres blobs; object storage backend is optional via configuration |
| Batch profile lookup | `GET /v1/profiles:batch` | `profile.Service.BatchGet` | none | `profiles` | index on `profiles.updated_at` useful for admin tools | Durable | Medium | Decision: return only existing persisted profiles; do not auto-create missing profiles in batch reads |
| Capabilities | `GET /v1/client/capabilities` | `capabilities.Service.Build` | none (config-driven) | none | N/A | N/A | High | No DB requirement for current behavior |
| RTC join-ticket replay guard | `POST /v1/rtc/channels/{channelID}/join-ticket` + signaling consume path | `rtc.TokenService` | `rtc_join_ticket_replay` (consume-on-parse) | `rtc_join_ticket_replay` | PK `jti`; expiry index | TTL-like | High | Needed for multi-instance replay prevention |
| Realtime chat presence/typing | `GET /v1/realtime` WS | `realtime.Hub` | none (ephemeral) | in-memory only | N/A | Ephemeral | High | Explicitly out of v1 persistence scope |
| RTC signaling room state | `GET /v1/rtc/signaling` WS | `rtc.SignalingService` | none (ephemeral) | in-memory only | N/A | Ephemeral | High | Optional audit persistence deferred |
| Optional auth identity mapping | auth middleware evolution | `middleware_auth` (future refactor) | `auth_identity_bindings`, `auth_sessions` | same | unique `(provider,provider_subject)`; active session indexes | Time-bounded + durable | Medium | `auth_sessions` is authoritative in Postgres; Redis is read-through cache for token/session lookups with invalidate-on-revoke; production token contract uses JWT |
| Optional AT Protocol handshake state | future auth endpoints | new auth service (planned) | `atproto_auth_requests`, `atproto_authorizations` | same | unique `state`; expiry indexes | Time-bounded + durable | Low | Decision: DID remains provider subject mapped to local `user_uid`; claim/scope contract remains TBD |
| User-created servers | planned `POST /v1/servers` | not yet implemented | `servers`, `server_memberships`, `users` | same | role and membership constraints | Durable | Medium | API contract and role model still to finalize |
| User-created channels | planned `POST /v1/servers/{serverID}/channels` | not yet implemented | `channels`, optional `channel_groups`, `channel_memberships` | same | position indexes, FK integrity, and strict per-group/category name uniqueness constraint | Durable | Medium | Decision: enforce strict channel-name uniqueness per group/category (case-folding details TBD) |
